# Email template authoring: mentions and realistic block previews

Status: design and implementation planning only; revised 2026-10-19. No application changes, browser checks or tests performed. Based on the current working tree, including existing uncommitted work. Applied the `ux-designer` skill; visual/accessibility behavior below is a requirement, not a verified property of the current UI.

## Intended experience

An organizer writes an ordinary email, inserts dynamic information with `@`, and sees where the actual payment or order section will appear. Internal `{{code}}` identifiers remain the storage/send contract; authors normally see localized names and illustrative values. Keep the existing template scope, inheritance, reset and save workflow.

Replace the large visible substitution inventory with short usage text and persistent helper copy beside the subject/body: **„Napište @ a vyberte údaj, který se doplní při odeslání.“** Add an accessible **„Vložit údaj“** action so discovery never depends on knowing the keyboard trigger. In the subject it opens subject-compatible fields; in the body it opens all fields supported by this template. Keep helper text available in fullscreen body editing.

## Mention chooser

- Open at the caret when an author types a fresh `@` at a strict authoring boundary: start of the editable text, whitespace, or approved opening punctuation with no preceding address/URL token. This is not a regex word boundary: a local-part ending in punctuation, such as `jana+@`, must not activate it. Do not trigger inside an email address, URL or existing mention, or when pasting an address. Do not interrupt IME composition. A literal `@` remains normal text if the chooser is dismissed. Decide trigger eligibility on the typed prefix before showing any popup, so `jana@` never briefly flashes the chooser while its domain is still incomplete.
- Filter locally by localized label, description and internal identifier. Normalize case and accents for search. Show a readable label, a short example/description and, when relevant, a textual „Již vloženo“ status. Distinguish „Přehled objednávky - odkaz“ from „Přehled objednávky - tlačítko“; their current catalog descriptions are identical.
- With no query, use two stable groups: „Doporučené“ for unused fields and commonly repeated text fields; „Již vložené bloky“ for already-used composite sections/buttons. Repeated text fields stay eligible and retain a small usage indicator. With a query, search relevance takes priority over usage ranking. Never silently hide used fields.
- Compute usage from the current draft, including an open body session. Rank in the active field: an occasion name in the subject should still be recommended in a body that does not contain it. Composite block duplicate counts concern the body. Counts refer to canonical occurrences, not preview fixture contents.
- Repeatable text examples: occasion title, name, order symbol, amount. Composite sections such as `fullOrder`, `paymentDetails`, `balanceReasoning` and `changeOverview` remain insertable again through the lower group. Repetition is discouraged by placement, never forbidden or confirmed through a modal.
- Keep ordering stable while the chooser is open except when the query changes. Display roughly six rows then scroll; do not cover the caret or overflow the editor/dialog viewport. At small widths, use a viewport-bounded panel above the soft keyboard with the same search and insertion semantics.
- Arrow keys change the highlighted result; Enter inserts it; Escape closes only the chooser; Tab closes it and follows normal focus navigation. Announce result count and active result without reading the entire document. Empty search: „Žádný odpovídající údaj“ with a clear-query action, leaving the draft intact.

## Inserted content and editing

Insert a localized inline token such as `@Název akce` for scalar values. Use restrained background/border styling and a semantic label such as „Proměnný údaj: Název akce“. Example values belong in the chooser or selected-token details, so sample text is never mistaken for a literal saved value. In a rendered email preview, substitute the example value.

Tokens are atomic for caret movement, selection, deletion and replacement. One Undo reverses the insertion or explicit replacement, including the typed trigger/query. Copying between Festapp template editors retains the canonical token; plain external text may expose `{{code}}` for lossless interoperability. Existing valid `{{code}}` text pasted or loaded in supported positions becomes the same token presentation. Unsupported placeholders remain intact and visibly identifiable, with a nonblocking explanation; opening or saving a legacy template must not erase them.

The subject accepts text-valued substitutions only. Exclude HTML sections, button fragments and HTML-producing link groups. Preserve existing unsupported subject content without silently converting it. URL-valued substitutions are scalar; body link editing should allow selecting them for the destination, preserving the current `href="{{code}}"` contract. A token in a link destination is not rendered as a body chip.

All token/editor metadata and sample values are transient. Save the exact existing identifier (`occasionTitle` versus `occasion_title`, for example), serialized as `{{code}}`; do not rename aliases, persist a preview card, or save editor-only `<div>` wrappers. Inline token insertion in styled text must preserve surrounding formatting; block insertion must split a paragraph at the caret without losing text on either side.

## Gentle suggestions for typed real values

Start with one deterministic, high-confidence case: the current occasion's full title, only when an occasion context exists and the template supports its title substitution. After the user completes the full literal title in editable text and pauses, show one low-emphasis inline suggestion below the active field: **„Použít proměnný název akce místo ‚[název]‘?“** Actions: **„Nahradit údajem“**, **„Ponechat text“**. No toast, modal, automatic replacement, caret jump or alert styling.

Offer only exact normalized full-title matches, avoiding URLs, attributes, existing tokens and incomplete words. No fuzzy/AI inference, partial-name guessing or suggestions based on recipient personal data. Do not scan and nag about all preexisting text on open. A short or generic title that creates ambiguous matches should not trigger the initial version.

Acceptance replaces only the identified occurrence in a single undoable transaction; it does not replace all occurrences. Before applying, revalidate the range against the current draft revision. If the author edits or leaves that occurrence, withdraw the suggestion. „Ponechat text“ suppresses that value suggestion for the editing session. It never blocks saving. Unit/organization contexts without a specific occasion use sample data but do not invent an actual-title match.

## Composite sections: illustrative inline cards

Render a supported HTML-valued substitution as an atomic, full-width editor block in its actual document position. Its chrome identifies the localized section name and **„Ukázková data“**. The interior shows recognizable email content, with no editable sample cells and no active payment or capability links. Selection offers accessible remove/cut controls; normal text can be entered before and after the block. Do not require drag-and-drop to reposition it.

Use one coherent fixture context across the entire draft: one occasion, one order symbol, two realistic admissions with product rows, a consistent total/currency and a valid example deadline. Avoid the model's current impossible `30. 2. 2026` sample. Any bank/QR depiction must be explicitly illustrative and non-actionable. A payment block should show the actual semantic fields for that template: amount, account/reference, deadline and the appropriate payment explanation. An order block must show the real renderer's grouped ticket/application rows, product descriptions and prices, contact information and total; do not invent quantity columns or other fields absent from the actual email HTML.

Critical mapping: confirmation payment instructions are carried by `balanceReasoning`, not by `paymentDetails`; `paymentDetails` is currently exposed for reminders. `fullOrder` means the order-details section, while `order_overview_button` is a customer overview button. These must not collapse into one generic "overview" variable. Respect each template's actual substitution set, including the waitlist confirmation's absence of payment information.

Use per-template fixtures for unpaid confirmation, order changes, paid confirmation and reminder where those variables are offered. `balanceReasoning` must illustrate its scenario-dependent output instead of always showing a payment table. Link/button fragments must preserve the appearance supplied by their actual producer, not an order table or an invented shared button. Fixture sections should tolerate long names, zero optional rows and narrow widths without horizontal editor scrolling.

Reuse the ticket editor's principle of context-driven live sample data (`resources.previewData(document, scenario)`), not its canvas layout or PDF UI. A complete subject/body sample preview is required alongside the inline cards: render the current unsaved subject and body through the same coherent fixture model, label it „Náhled obsahu e-mailu - ukázková data“, and keep editor-only card chrome out of it. It must reflect open body edits as well as subject changes. Server-resolved wrappers and banners are out of scope; this preview is illustrative and does not claim exact delivered-email fidelity. Do not add a scenario toolbar unless scenarios materially change the available template's rendering.

### Concrete HTML fidelity and noninteraction contract

Render actual HTML fragments generated from the owning TypeScript producers with deterministic sample inputs. Generate these fixtures during development/build tooling and consume the resulting local artifacts; do not reproduce email tables/buttons as hand-built Flutter layouts, duplicate financial calculations, or request a live preview endpoint. The same generated fragments feed inline blocks and full subject/body preview. Identify fixtures by producer/template/scenario/locale, since one variable code can have different presentation across producers. Regeneration and a scoped freshness check must reveal producer changes that would leave examples stale.

The generator invokes the actual pure `generateFullOrder`, `generatePaymentDetails`, translation and `generateChangeOverview` paths and bundles deterministic JSON by template, scenario, delivery locale and tone, including scalar values and fragments from one dataset. Extract action-anchor markup into the pure shared `emailActionLink.ts` helper while preserving existing variants: plain standalone overview link and styled waitlist button. This extraction changes ownership/reuse, not the delivered appearance.

`generateFullOrder` in `supabase/functions/_shared/orderOverview.ts` produces a light gray bordered card: order heading, optional recipient details, grouped tickets/applications, product rows and a right-aligned total, with optional surcharge annotations. Preserve this composition and its inline CSS. It does **not** contain an overview button; do not add one inside its preview. For a concrete sample, use a fictional person such as Jana Nováková (`jana.novakova@example.invalid`), two distinct admission symbols and products priced 450 Kč and 350 Kč with an 800 Kč total. All payment/order examples must use the same values. Let the real renderer choose labels and money formatting; the fixture is data, not a second email layout.

`prepareOrderOverviewEmail` in `orderOverviewEmail.ts` currently emits `order_overview_button` as an ordinary unstyled `<a>` with the label „Přehled objednávky“. The preview for `ORDER_OVERVIEW` must show that link honestly, despite the internal name. In contrast, `waitlistEmailRenderer.ts` emits overview/manage/offer anchors with `display:inline-block`, 12px/20px padding, blue `#1565c0` background, white text and a 6px radius. Those appear as real email buttons, with precisely those source styles. Giving the standalone overview email the same styled button would be a separately explicit production-rendering change applied to both send output and generated fixtures; a preview-only visual upgrade is unacceptable.

The waitlist renderer may append an overview button when it is missing from rendered HTML. The complete waitlist sample must include this known producer-owned fallback when its fixture context contains an overview URL, and omit a duplicate when a matching link is already present. The canonical pure TypeScript `emailContentCompletion` helper consumes producer-owned required-link data `{url, html}`; the build-time generator exports those data and expected fixtures. A small generic Dart composer implements that fixed completion contract for the live draft, with TS/Dart parity coverage for present, missing and unavailable links in both full documents and fragments. Flutter does not run TypeScript live. Prohibit independent waitlist state decisions, duplicated link layout or a broad rule language; this narrow shared-data protocol is allowed. The inline variable card remains just its own fragment. This preserves what the selected template actually sends without inventing a combined order-table/button variable.

The shared `HtmlView` is not a faithful inert email surface today: it calls `linkifyHtmlText`, applies application link colors, uses `HtmlWithAppLinksWidget` navigation, custom image zoom widgets and mobile YouTube embedding. Use a dedicated `EmailPreviewHtml` adapter over the existing `HtmlWidget` library, skipping those app-content transformations. Honor producer inline colors, padding, borders and typography on an email-colored canvas even when the surrounding app uses dark mode. Do not globally change normal `HtmlView` behavior. Flutter's HTML/CSS support still bounds visual fidelity; identical source markup is not a guarantee of identical pixels across email clients.

Buttons/links must look like the real email but remain non-actionable: preserve their visual markup, neutralize URL dispatch for pointer, keyboard and accessibility activation, and expose no navigation/click semantic action. Do not use disabled Material buttons, gray out source colors or remove all HTML semantics with a blanket exclusion. Keep readable text and a concise semantic note such as „Ukázka tlačítka Přehled objednávky, odkaz není aktivní“. Card selection/removal and preview scroll remain active controls outside the inert content. Remove anchors from tab focus while keeping their labels in reading order. Block real capability/payment destinations; use inert example URLs and sample data at the fixture boundary. No send, payment, deep-link navigation, video embed or image zoom may be initiated by preview content.

Use a fit-to-container view for inline cards and a readable email-width canvas for the complete preview. Show essential card content rather than a miniature screenshot or generic placeholder; long generated sections may have an explicit expand/collapse control. Keep the sample-data label outside the rendered fragment so it neither changes layout nor masquerades as sent content. For unsupported HTML/CSS, preserve the source and report the concrete renderer limitation instead of silently replacing the section with a redesigned card.

## Pinned upstream primitives and integration choice

Source inspection of `/Users/miakh/.pub-cache/hosted/pub.dev/super_editor-0.3.0-dev.52` corrects the initial reconnaissance: this version already exports `StableTagPlugin`, `ActionTagsPlugin`, `PatternTagPlugin`, `AttributedTextBoundsOverlay` and inline widget builders. The absence of the word "mention" in a scoped search was not evidence of absent tag support. No dependency upgrade is justified by this feature alone.

The upstream `example/lib/demos/in_the_lab/feature_stable_tags.dart` demonstrates a composing-state listener, `AttributedTextBoundsOverlay` plus `Leader`/`Follower`, popover selection/cancellation, attributed styling and `FillInComposingStableTagRequest`. Reuse this overlay/focus architecture with Festapp's localized catalog and ranking. The demo's `PopoverList` is an example component, not an assumption of a public ready-made menu; Festapp owns its accessible menu rows. Preserve existing caret/selection overlays when adding the composing anchor.

Recommended integration is **`ActionTagsPlugin` for temporary `@` composition plus an explicit domain insertion transaction**, using a custom `TagRule(trigger: '@', ...)`. The chooser represents a command to insert a known substitution. A selection commits it; ordinary space, punctuation, blur or leaving the range must never turn arbitrary text into a template variable. Set the rule to stop composition at whitespace for the initial scope: localized labels can contain spaces, while authors search by a word or identifier. If multi-word queries are later desired, require an explicit rule/UI change rather than accidental stable-tag auto-commit.

Do not use the pinned `SubmitComposingActionTagRequest` unchanged for `@`: its `SubmitComposingActionTagCommand` searches with `defaultActionTagRule` (`/`) despite a plugin's configurable rule. Instead use the plugin's composing range, revalidate it, and replace it with the selected domain token/block in one editor transaction. This small explicit command also controls spacing and undo. Cancellation can use the supplied `CancelComposingActionTagRequest(customRule)`; ensure leaving the range preserves literal query text and cancelled input does not reopen until a new trigger is typed. Filter composing activation at the app boundary to exclude addresses, URLs and IME composition.

`StableTagPlugin` is useful evidence and a viable alternative only with an explicit adapter. It provides `StableTagIndex`, committed immutable spans and `AdjustSelectionAroundTagReaction`, but its default `TagUserReaction` automatically commits when selection leaves a composing range (including typing an excluded space). `FillInComposingStableTagRequest` uses one string for both visible text and `CommittedStableTagAttribution.tagValue`, inserts `@value` plus a trailing space, and its cleanup deletes a committed tag if displayed text differs from `tagValue`. Therefore passing canonical `occasionTitle` as identity while showing `Název akce` cannot be achieved by simply changing that request's label. Do not attach stable and action composition for the same trigger. `PatternTagPlugin` provides automatic tagging, not the explicit catalog selection and immutable domain identity needed here.

For committed scalar chips, prefer the existing `AttributedText` placeholder-object support plus `Styles.inlineWidgetBuilders`/`InlineWidgetBuilderChain`: one model position stores a domain object containing canonical code; its Flutter widget displays a localized multi-word label with semantics. This separates identity from display text and avoids stable-tag label validation and whitespace parsing. It is a real upstream extension point, but requires Festapp's HTML codec and clipboard adapter to encode/decode `{{code}}` rather than the placeholder character. Verify caret, selection, deletion, line wrapping, copy and screen-reader behavior for the one-position object before adopting it broadly. Full-width composite previews remain domain block nodes, not inline widgets. Do not retain an invisible canonical-text overlay solely to disguise a tag label; it risks text geometry and accessibility mismatch.

Escape needs an explicit interaction guard: Festapp's `_cancelShortcut` handles key-down and may cancel the parent, while both tag plugins' stock Escape handlers act on key-up and halt even without active composition. Route an open chooser's Escape key-down before `_cancelShortcut`, cancel composition, consume the matching key-up, and return focus to the caret. When the chooser is closed, delegate Escape to the existing parent behavior. Do not assume stock plugin handler ordering satisfies this. Reuse `SuperEditorPopover` for editor/popover focus linkage and handle Up/Down/Enter only while the menu owns those interactions; Tab must retain the specified normal traversal behavior.

For the subject, prefer the same Super Editor authoring core constrained to one plain paragraph, rendered inside the existing labeled field shell without a formatting toolbar. This reuses the action plugin, explicit insertion transaction, domain placeholders, chooser, clipboard and editor history. Enforce one paragraph at the input boundary for keyboard Enter, IME and paste; normalize pasted newlines to spaces and strip rich formatting while preserving allowed tokens. This is a text-only storage adapter, not HTML subject storage. `SuperTextField` does expose `AttributedTextEditingController`, `inlineWidgetBuilders` and `maxLines: 1`, but has no `SuperEditorPlugin` interface, and the inspected controller has no corresponding editor transaction/history API. It would require a second composing/insertion/history adapter to meet the same Undo contract. Favor sharing the existing document-based machinery over that duplication; verify the subject's field semantics and one-paragraph constraint in the focused implementation step.

Use `InsertInlinePlaceholderAtCaretRequest` where it fits the explicit replacement transaction; a one-position placeholder does not need `AdjustSelectionAroundTagReaction`. The latter belongs to attributed multi-character stable tags. Local upstream source evidence: `lib/src/default_editor/text_tokenizing/{stable_tags,action_tags,pattern_tags}.dart`, `lib/src/default_editor/text.dart`, `lib/src/infrastructure/popovers.dart`, the stable-tags demo above, `test/super_editor/text_entry/tagging/stable_tags_test.dart`, and `test/super_editor/text_entry/inline_widgets_test.dart`. Upstream tests are available as behavioral reference; they have not been run for Festapp's integration. This is source-based feasibility evidence, not a claim that the integrated behavior has been tested.

## Acceptance scenarios for implementation

1. Open and save an existing template without editing: identifiers, URL placeholders, inheritance and surrounding email tables remain unchanged; sample values/editor wrappers never reach stored HTML.
2. Type `@` in subject/body, search without Czech accents, insert with keyboard and touch, then Undo/Redo. Subject does not offer HTML blocks. Typing an actual email address does not open the chooser.
3. Insert the occasion title in the subject, then open the body chooser: it remains recommended. Insert `fullOrder`: it moves to the used-block group, remains searchable and can be inserted again. Removing the last occurrence restores its unused ranking.
4. Confirmation shows a coherent `balanceReasoning` payment example and `fullOrder` order example; reminders use the appropriate `paymentDetails` example; paid and waitlist messages show no misleading unpaid payment card.
5. Type the current full occasion title: accept or dismiss the unobtrusive suggestion; only the intended occurrence changes; Undo restores the literal. Edit the range before accepting: stale replacement cannot affect new text.
6. Select/delete/copy tokens and block cards, edit text on either side, paste existing placeholders, edit a link destination, and expand/collapse the body editor. Draft, selection and canonical token identity remain intact.
7. Keyboard-only and screen-reader use exposes chooser results, localized token names and card actions. Escape closes the chooser before any parent dialog; focus returns to the insertion point. Visible focus, non-color status and readable contrast are mandatory.
8. At 320px width, 200% text scaling and with long localized labels, chooser/helper/cards remain usable; no obscured caret, clipped primary action or dependence on hover. Touch controls use the existing Material sizing convention, targeting 48dp.
9. Open the complete sample preview after changing the subject and an unapplied body session: both show current draft content with matching sample values. The preview contains neither editor chrome nor live actionable payment/capability links, makes no server-wrapper/banner request, and opening it does not save the template.
10. Preview generated `fullOrder`: real grouped rows, recipient, symbol and 800 Kč example total appear, with no invented overview button. Preview `ORDER_OVERVIEW`: show its actual plain link. Preview a waitlist fixture: show its actual blue/white buttons, including the renderer-owned missing-link fallback once, never twice. A producer styling change updates generated fixtures and both preview surfaces together.
11. Try pointer click, Enter, Space and screen-reader activation on each preview link/button. No route, new tab, URL launch, form submission or capability call occurs; labels remain readable and the editor's own controls remain operable. App dark mode must not recolor the email button text using the application link color.
12. Type `jana@`, `jana.novakova@`, `jana+registrace@`, `jana+@`, and complete `jana@example.cz` in subject/body: no popup appears at any intermediate step. Paste an address or URL containing `@`, move the caret through one and edit its domain: no popup. At a fresh allowed boundary type `@nazev`: the chooser opens and insertion still works; inside an active IME composition it waits until composition is safely committed.

## Remaining implementation decisions

- Prove the upstream inline-placeholder representation and explicit action-tag insertion transaction with exact AST/clipboard round-trip in a small focused implementation step. Upstream supplies the primitives; Festapp must provide domain serialization and interaction integration.
- Confirm the actual value kinds and scenario output for every descriptor against the current producers before finalizing the subject allowlist and fixtures. The existing strings are not sufficient evidence.
- Required scope includes scalar chips, realistic inline cards and the complete subject/body sample preview. Server-resolved wrapped-email/banner preview remains out of scope.
- Parent-draft tracking must include subject changes and open editor changes before claiming discard protection or usage counts are complete; the current subject is saved only through the form's `onSaved`.
