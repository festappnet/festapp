# Scanner access belongs to one occasion

Status: implementation and release in progress. Verification: standard; mandatory release gates remain required.
Scope: shared code on main, production web tenant festapptickets / organization 3 only. Do not rotate credentials or deploy clients for other tenants.

## Result and invariant

A code identifies exactly one occasion or grants no access. Copying an event never copies scanner access. Rotation changes only the chosen event. A random collision, including concurrent requests, cannot allocate an existing code. Back navigation is bound to the authenticated scanner occasion rather than a previously selected event.

## Evidence

- Country ball 32316 historically shared hidden row 1 with 13, 82 and 11438. Its independent hidden row 37 is now live. The interim 32-character credential has been replaced by the established five uppercase alphanumeric characters; the interim credential is invalid. See the operational receipt.
- All live copy overloads delegate to the current three-argument `duplicate_occasion_internal_v1`, which inserts NULL for `occasion_hidden`. Historical rows were not repaired by that code correction.
- `get_scanner_occasion_for_scan_code_internal` previously returned multiple occasions; modern bootstrap and legacy entry/export selected one. Old direct ticket operations also compared the shared secret without uniqueness proof.
- `scanner_navigation.js` used one global `festapp-scanner-return` key. An isolated live browser reproduced Country ball returning to Skautsky's ticket page. Explicit Country returnTo worked.
- Flutter's `TicketCodeHelper` allocated five characters with client-side `Random()`. It had no database uniqueness guarantee and initialization was a read followed by an independent write.

## Execution

1. **Contain the incident - applied.** Country ball has independent access, five-character format, old interim code revoked. Preserve other event credentials in this incident repair. Fetch the new Country link from the admin dialog; never retain secrets in repository receipts.
2. **One proof and allocation owner.** Reject ambiguous and empty proofs in the private resolver. Route entry/export, legacy ticket/admission/password operations and existing scan-link sessions through it. `update_scan_code` remains a bounded supported-client adapter and sole write owner. `get_or_create_scan_code` locks the stored occasion, reuses existing access on initialization and performs server-side cryptographic generation on rotation. Database unique index on non-NULL `occasions_hidden.secret` arbitrates concurrent collisions; retry generated collisions, return 409 for caller-supplied collisions. Ordinary rotation refuses a historical shared relationship with `shared_scan_credential`; gradual splitting must not reactivate the old known credential for the last remaining event. Only an explicit whole-group repair may retire and replace those credentials. No global writer lock or application trigger.
3. **Bind navigation.** Include canonical `occasion_link` in session data. Recompute return path on every selected/restored session. Store per backend/generation/organization/occasion; accept only same-event return paths. Ignore the obsolete global key. Old cached sessions missing canonical metadata return home until refreshed. Preserve current scanner input/browser-history behavior.
4. **Verify and release.** Register the regression test in canonical CI inventory and the occasion lifecycle group. Tests must cover historical sharing, legacy consumers, old sessions, independent rotation, database duplicate rejection, forced generator collision/retry, concurrent collision and concurrent initialization, five-character format, stale cross-event storage/explicit returnTo, reload and existing scanner browser history. Run affected canonical CI mirror lanes before source publication. Fetch/reconcile current main, publish shared code, require every canonical GitHub job on exact main SHA before preparing/pushing the single selected tenant overlay. Apply exact reviewed forward migration and ledger atomically through the canonical backend workflow before releasing the new client RPC caller. Build locally and deploy directly; verify live code format, API scope and real browser Back behavior.

## Database ownership contraction

The first package prevents accepting ambiguous historical access and rejects duplicate secret values. It does not yet make `occasions.occasion_hidden` globally unique. Completion of that schema invariant requires a separately scoped historical credential migration, not an arbitrary oldest-event winner.

Before contraction, inventory every shared hidden row and every duplicated secret without exposing secrets. Every credential known to multiple events must be retired for the entire group; allocate independent new credentials, bump epochs/revoke existing scan-link sessions and require redistribution. Do not preserve the old shared credential for one winner: users of the copies also know it. Repairing only one event cannot revoke that previously disclosed capability for the remaining group.

The prior read-only inventory found additional groups in organization 3 and one two-event group in organization 5. Refresh that inventory before any data writes. Organization 5 credential changes are outside the selected tenant's authority and are a genuine scope gate. Never silently rotate that tenant's access or claim global historical cleanup completed.

After all affected tenant scopes are authorized and repaired, add a database unique constraint/index on non-NULL `occasions.occasion_hidden`; retain the globally unique secret constraint. Prove direct attempts to attach an existing hidden row to a second event fail, including a regression in the copy function. Validate existing FK/orphan state before adding anything redundant. Keep this contraction pending explicitly until no shared rows remain; do not introduce a permanent per-tenant exception, a partial uniqueness index excluding contaminated IDs or an application trigger.

## Completion and rollback

The current release is complete only with verified main/tenant/migration identities, public API and browser evidence. Global historical isolation is a separate unfinished gate until the ownership contraction above is applied. Keep this distinction in the handoff.

On failure, roll back the code/client release using supported release tooling. Preserve database uniqueness and revoked credentials; never restore a known shared or leaked credential as rollback. A migration failure must roll back SQL and its ledger together. Do not manipulate other sessions' worktrees, fixtures or Flutter processes.
