# Reduce repeated Supabase query work in Festapp

Date 2026-11-25. Verification standard. Baseline source is authoritative main at `390414f9f7`. Runtime evidence is from the canonical shared Supabase database and editor timing samples are from vstupenky.online.

## Outcome and scope

Reduce database latency when opening and saving a form. Establish the production origin, recent impact and safe next action for the other expensive queries observed on 25 November. This is a SQL performance change. Preserve all existing entry points, authorization, deletion guards, payment policy, data shape, mutation receipts, and delivery guarantees. The production database also serves other tenants, so a shared SQL release requires the canonical database release workflow.

## Wave 1 - Form editor and acknowledgements

- Production tracking counted seven calls to `get_form_editor_bundle_internal` from a single call to `get_form_authoring_snapshot_internal`. The SQL planner expands references to the expensive expression in the inline subquery. A read-only comparison with one materialized row took 81 ms versus 592 ms on a form with 164 orders and 270 ms versus 2,033 ms on a different sampled form. Both result objects matched when excluding the time generated during calculation.
- In `database/functions/eshop_forms/admin_form_reads.sql`, materialize the one-row bundle inside the canonical snapshot function. Use the existing projection and 200-code filter. In `database/functions/eshop_forms/admin_form_orders.sql`, materialize the snapshot once before extracting administrative order facts. Those facts enter the existing preview confirmation hash. Keep the hash inputs, stable transaction snapshot and authorization decisions.
- Register an append-only forward migration selecting only the two changed routines in `automation/migration-forward-owners.json`. Keep sealed history and the current ACL. No data rewrite is required.
- Extend the owned form authoring SQL test with a call-count regression at the expensive builder boundary. Exercise an authorized form read and successful save through existing RPCs, and the administrative order-facts projection. Retain parity and failure cases, and confirm the regression fails against the old body. Run the affected SQL and migration ownership checks against the local disposable runtime.

## Execution evidence

| Surface | Evidence and decision |
| --- | --- |
| Form editor | The disposable predecessor failed at seven builder calls for one authorized read. The administrative order projection separately reproduced 21 builder calls and 1.80 s on production. The forward migration passed the regression suite with one call each for reading, saving and administrative order facts. The read-only production comparison matched both payloads after removing the generated time field. |
| 52-second operator query | The six recorded runs included `get_form_authoring_snapshot_internal` for every matching form and performed about 34.7 million shared buffer accesses per run. This exercise compounds the snapshot evaluation bug. The fix reduces that repeated work. An operator-wide replay and attribution of the remaining baseline cost are pending live release. |
| REST gateway | A bounded observation identified Envoy sending requests to PostgREST at five-second intervals. Installed CDS confirmed GET `/`; public proxy logs independently contained only unsuccessful root requests during the sample. Five direct GETs per path gave medians of 125.5 and 1.9 ms, with HTTP 200 on both and `[]` from the replacement. Exact pinned Envoy recognized healthy, failing and recovered states using the generated path in a disposable replay. |
| Notifications | Last 24 hours: 85,504 wake runs, p95 38.5 ms, max 294.9 ms, zero failures. In one reused read-only connection, 13 calls averaged 9.9 ms with zero worker dispatches. A fresh plan took 28.4 ms. This supports keeping the recovery interval while distinguishing session overhead and predicate work. The removed daily overview RPC is present only in historical aggregates. Its live successor had p95 194 ms on 115 recent public gateway requests. |
| Abuse and email cron | Abuse jobs had p95 217 ms over 1,440 runs. Indexed transaction and bank-identity checks finished in 3.7 ms for the largest sampled unit, even with 535 correlated payment checks. Email queue recovery had p95 281 ms and no errors over the same period. The evidence supports keeping the existing safety work. |

An alternate email query selected fewer columns and matched the sampled output, but ran more slowly in both comparisons. Keep the original email query. Historical checkout averages were 340-344 ms, with an anonymous maximum of 923 ms. The retained gateway window did not contain a successful checkout call under this RPC. |
| Startup | The recent `get_app_config_v219` gateway sample had median 30 ms, p95 476 ms and max 1.06 s over 750 requests. The historical 7.93 s SQL peak lacks request-level attribution. Its unit route can load a dashboard in the same RPC, so a single isolated test of another route cannot establish the cause of the tail. |
