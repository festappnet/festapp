# Order switching on Tickets and places - 2026-11-02

Reported surface: switching exact orders while retaining the tickets tab. An isolated muted headless browser reached sign-in and had no authorized session; it was closed. Authenticated browser click-to-paint latency has not been measured. The reproduction instead drives the actual OrdersContent grid/router/controller/viewer, with real response decoding and a deterministic server fixture.

Baseline production diagnostics were explicitly read-only, scoped to the reported order/occasion/org on the verified canonical backend. Three DB-only samples: admin detail 47.73 / 18.87 / 19.15 ms, map 67.34 / 52.06 / 51.16 ms. The map returned about 509 kB every time: 131,167 geometry bytes and 348,183 rendering-resource bytes, plus current seat facts for 228 seats. It had no bitmap assets. Thus repeated drawing download/JSON preparation was demonstrated; server times are not network/UI latency.

The actual switching regression went red because the second map request had no known revision and downloaded unchanged drawing data again (/tmp/order-switch-perf-red.log). The screen now owns a bounded three-plan cache of immutable drawing/resources and parsed documents. Each order still loads its own authorized detail and map occupancy; the map validates read permission and the unchanged placement fingerprint. A matching saved revision omits static drawing data, while any changed revision returns complete new drawing data. The client retains the request's exact immutable snapshot across cache eviction and rejects scope/revision mismatches or missing data. Drawing resources use the existing core deep-freeze helper; per-order metadata excludes drawing blobs and cannot replace its top-level values. The controller keeps its current-order preview store private. A geometry-save race between the core and map reads refreshes core metadata once and reuses the newly received drawing for the retry. Disposal/context changes prevent late results from entering the cache or wrong viewer.

The detail initially constructs only the selected tab; the hidden Overview form is created when first opened, while visited tabs keep their edits.

A shared private placement projection now supplies the exact original tickets/places/plans/fingerprint to both readers. It does not duplicate the full email, payment or form read during the map request. A disposable before/after test loaded old canonical SQL, captured the full admin response, installed the new SQL in the same transaction, and verified byte-for-byte JSON equality, including the fingerprint. It then ran the standard SQL reader test and rolled back.

For the frozen reported response, the conditional shape is 29,883 bytes versus 509,260 bytes, a 94.1% reduction. Locally gzip-compressing those JSON bodies produced 6,534 versus 86,129 bytes (illustrative compression, not a measured HTTP encoding). A 30-iteration native Flutter debug replay measured JSON/document preparation at 8.975 ms for full decode/parse and 0.143 ms for conditional decode/reuse. These are preparation-only measurements, not browser rendering or end-to-end speed claims. The private snapshot remains outside the repository.

Coverage includes cache scoping/eviction/late reads, real grid/router order switching with fresh occupancy and revision invalidation, existing preview behavior and draft saves. Disposable SQL tests passed: conditional payload, legacy default-argument calls, revision miss, current/expired occupancy, auth/foreign-plan guards, private helper ACL, single function signature, read consistency and mutation-free reads.
