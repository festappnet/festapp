A webhook sends your application a message when an order is created, so you can update your own records or start further processing without repeatedly fetching orders.

This guide is for your integration developer. Order creation does not mean payment. The current events are net.festapp.order.created.v1 and the synthetic test event net.festapp.webhook.test.v1.

Technical reference and availability

Open the automatically generated API reference. The webhooks.* operations manage subscriptions; the Webhooks section describes messages sent to your server. Machine-readable schemas are available as OpenAPI JSON. Schemas come from the same definitions that validate outgoing data.

Documentation alone does not confirm that webhooks are enabled for your connection. Ask your integration administrator to verify availability and register an API client with the operator profile, the required webhooks.* operations and scopes. An ordinary Make order-summary connection does not provide this access.

1. Prepare your connection and receiver

Follow the reference's OAuth flow, sign in and consent to access for the selected event. The client needs festapp:ticket-layouts:read, festapp:orders:read, festapp:webhooks:read and festapp:webhooks:write. You also need current order-management permissions for that event. Request authentication follows the client registration; the linked reference describes the DPoP profile.

Prepare a public HTTPS endpoint on port 443, such as https://your-service.example/webhooks/festapp. Redirects and local or internal destinations are unsupported. Agree on the event, optional form, destination and handling of disclosed personal data before creating a subscription.

2. Create a subscription

Send an authenticated POST /operations/webhooks.create to the API base address in the reference. This example represents the Willow Hall Ball form. Replace the event and form IDs and generate your own commandId UUID.

{
  "occasionId": 7,
  "formId": 12,
  "commandId": "11111111-1111-4111-8111-111111111111",
  "expectedContractVersion": 1,
  "eventTypes": ["net.festapp.order.created.v1"],
  "url": "https://your-service.example/webhooks/festapp"
}

Omit formId to cover the selected event's forms. Save data.subscription.id, version, expiresAt and data.signingSecret from the response. Keep the signing secret in protected storage, outside chats and logs. It is returned on creation or rotation, including authorized replay of the same command. After an uncertain result, retry the identical body with the same commandId.

3. Verify and durably accept messages

Messages use an immutable CloudEvents envelope with id, source, type, subject, time and data. Order data includes identifiers, buyer contacts, responses and individual tickets. Consult the generated reference for complete schemas and required fields. Admission QR symbols and payment credentials are excluded.

  1. Verify the signature over the original body bytes

    Use webhook-id, webhook-timestamp and webhook-signature. Standard Webhooks signs webhook-id.webhook-timestamp.body using HMAC-SHA256 and the base64-decoded key after whsec_. Check a five-minute timestamp tolerance and compare signatures in constant time. Parse JSON only after verification.

  2. Store the message and prevent duplicate effects

    webhook-id stays stable on retries. The event's source and id together identify the same occurrence across subscriptions. Messages can arrive more than once and ordering is not guaranteed.

  3. Acknowledge acceptance

    Return 2xx after durable storage and perform business actions asynchronously. The total request timeout is 10 seconds.

Download the Node.js receiver example. Use Node.js 24, supply the existing signing key through the protected FESTAPP_WEBHOOK_SECRET environment variable and run node webhook-receiver.mjs. The example listens on 127.0.0.1:8443 behind your HTTPS reverse proxy, verifies signatures and stores messages in SQLite before returning 202. Set FESTAPP_WEBHOOK_INBOX to choose the database path. Implement your business processing separately and protect the stored personal data.

4. Test the subscription

Call webhooks.test with occasionId, subscriptionId and a new commandId. This queues a synthetic event; accepting the command does not prove delivery. Inspect webhooks.deliveries and verify the stored message in your receiver. The test event contains no real order. After successful delivery, verify the complete business flow in a test environment.

Management, retries and troubleshooting

  • Subscriptions and changes: webhooks.list returns state and version. webhooks.update changes the URL or active/paused state; webhooks.delete ends the subscription. Changes require the current expectedVersion; reload after conflicts. Create another subscription to change scope or event type.
  • Failed delivery: up to 16 attempts run within 72 hours with increasing delays. HTTP 410 disables the subscription; other unsuccessful responses retry. Check DNS, public HTTPS access, certificates, signatures, server time and webhooks.deliveries history.
  • Manual redelivery: webhooks.redeliver starts a new series for a retained completed or exhausted event. Keep deduplication in place. Event data remains available for 7 days; safe delivery metadata for 30 days.
  • Key rotation: webhooks.rotate_secret returns a new secret with a one-hour overlap for the old key. Prepare your receiver to verify the new key and preserve deduplication during replacement.
  • Expiry: monitor the saved expiresAt. A subscription belongs to its original connection and permissions; an ordinary OAuth token refresh does not extend it. Prepare a replacement before expiry. Pausing or creating a new connection does not backfill missed orders.
